# Registry health

## In plain terms

`codument doctor` is test coverage for your docs: a deterministic gap-finder that tells you which areas are undocumented, stale, or missing dependencies, and which docs have rotted into noise. It does not judge whether the prose is good. It runs entirely locally with no network and no AI model, so the same repo state always produces the same numbers. Open it when you want a single honest signal of how well the registry and docs track the code, or a CI gate that fails when registry health regresses.

## Design approach

The whole frame is the test-coverage analogy. Coverage tooling never claims your tests are good; it reliably tells you what is *un*-tested. `doctor` makes the same trade for documentation: high coverage does not certify quality, but low coverage reliably means undocumented or stale code. That honesty is the product, so the command reports evidence ("here are the repo facts and suspicious gaps"), never a verdict ("this is safe").

Coverage and lint are two **separate** channels that are never merged into one number. Coverage is a scored ratio (registry membership and dependency declarations); lint is ESLint-style findings that flag mess and integrity gaps (bloat, duplicate/orphaned mappings, generated leakage, a doc claimed done but never narrated, a dangling intra-repo link, a dependency edge into nothing, a doc page no entry owns). Folding bloat into the coverage percent would make a single number mean two incompatible things, a gradient and a discrete count, so each keeps its own shape.

The denominator is the load-bearing design choice, because "what should be documented" is a judgment, unlike "every executable line." That judgment has two halves. The half codument can make for everyone is a canonical, version-controlled exclusion spec that removes generated, build, and test files (test suites and fixture trees alike) plus trivia, and that *same* spec is applied to both the numerator and the denominator (and shared with every other analyzer, the change-control gate, and the editor nudge hook, while `scan` goes further and shares the analyzer's whole walker, gitignore subtraction included, rather than re-deriving discovery from the spec alone; the governed families are the full module-flavored JS/TS set — declaration artifacts of any flavor excluded — Python (pytest conventions and environment trees excluded), Go (`_test.go` excluded), Rust (Cargo's crate-root `tests/` and `benches/` trees excluded), C#, the JVM pair Java and Kotlin (`src/test` source sets and `*Test`/`*Spec` files excluded), and the single-file component formats `.vue`/`.svelte`/`.astro`). Rejected: a per-analyzer file list, which lets coverage, lint, and the change-control gate silently disagree about what counts.

"Test file" here means one a language's own convention *names*, and the built-in spec goes no further than that — because the half codument can make for everyone is exactly the half where a language has already decided. A convention expressed as a directory is therefore anchored where the language applies it (Cargo's law holds at a crate root, so a workspace member's tests stay governed and that project declares its own pattern) rather than matched anywhere in a tree: `tests`, `test` and `spec` are ordinary words, and a lab, exam or assessment product has real domain code under them. The consequence is deliberate and cuts the way that keeps the tool honest — a first-party module that merely lives beside tests, a shared harness other code must satisfy, stays governed source rather than being silently dropped. Where a project's own test helpers escape every convention, that is the second half's job: declare them, visibly, in the project's own additive `exclude`. Rejected: excluding on a bare directory name, which buys a slightly tidier default by silently un-governing whatever product code happens to sit under it — the failure the score cannot report, because a dropped file leaves the denominator too.

The half codument cannot make is the project's own: a compiler output directory or a deploy tree is legitimate, unguessable, and named differently in every repository. A project therefore declares its own additions, which widen the built-in spec rather than replace it. Additive-only is the deliberate constraint — configuration can say "this too is not documentation", never "this built-in exclusion does not apply to me" — so no project can quietly re-admit test files or declaration artifacts into a coverage number, and the spec's floor is the same everywhere. The extension list stays out of configuration entirely, because it is the language matrix's truth: letting a project add to it would let codument claim support for a language it has no adapter for. Rejected: an invocation flag, which would let two runs of the same commit disagree about scope; the declaration is a repository artifact a reviewer sees in the diff, at the same trust level as the registry itself.

The dependency signal reads the registry graph, not the source: an entry others depend on is a foundation layer, and a foundation legitimately depends on nothing. So a foundation — an entry with inward edges but no declared dependencies of its own — is a vacuous case, excluded from the dependency-coverage denominator rather than scored as a miss, and never raised as an empty-depends-on finding. The genuinely suspicious case is an *isolated* entry: real code that nothing depends on and that depends on nothing, the signature of a forgotten wiring edge. This keeps the foundation utility layer from permanently dragging the score and tripping `--strict`, which would train the team to add junk dependencies or ignore the gate.

The rolled headline is the equal-weight average of the ratios that have a non-empty denominator. A ratio whose denominator is zero is excluded from the average entirely — never counted as 0% or 100%, which would lie — keeping the headline well-defined and free of NaN. The score is a pure function of repo state (filesystem plus git plus registry): no wall clock feeds it, so any time window is commit-count based, not duration based. Timestamps may stamp a trend record but never enter the number.

`--strict` is the only opt-in gate and it is deliberately narrow: it fails on actionable lint findings this change produced, never on informational notes (silencing an awareness-only signal must never be a way to pass), never on the debt the repo arrived with, and never on the coverage gradient (a coverage floor would be a separate concern). Bare `doctor` stays warning-only so the default stance is informative, not blocking.

The badge is a coverage figure, not a quality or correctness score, and absolute cross-repo comparison is not meaningful — so it must be earned by backtesting that the score moves at the right moments against real git history before it is ever exposed publicly. It renders as a hand-rolled static SVG with no network and no required dependency.

## Invariants & boundaries

- `doctor` runs with no network and no AI model, and is a pure function of repo state: identical inputs yield an identical report and score, independent of run, filesystem-traversal order, or wall clock. *(tests: `analyze.test.ts` determinism + rollup-order suites; `doctor.test.ts` "is deterministic across runs")*
- The exclusion spec is applied to both numerator and denominator: a generated or test path filters out of the in-scope set even when some registry entry lists it as a source. *(test: `analyze.test.ts` exclusion-spec and coverage-ratio suites)*
- **The scope every consumer applies is the built-in spec widened by the project's own declaration, resolved from one place.** Coverage, the lint net, the change-control gate, history audit, `scan` discovery, language detection, and the editor nudge all read the same resolution, so a declared build tree cannot be scored by one surface and proposed by another. Declaring nothing is byte-identical to having no declaration at all — the defaults are the floor, and configuration can only widen them, never narrow or replace them. *(tests: `analyze.test.ts` "resolveExclusionSpec widens the defaults, never narrows them" — defaults preserved, extensions untouchable, no shared-array aliasing; `scan.test.ts`, `doctor.test.ts`, `review.test.ts`, `hooks.test.ts` declared-scope suites, each pinning an unconfigured run as identical)*
- **A workspace score is named as an aggregate.** When the root is a workspace of nested member repositories, `doctor` prints the member list beside the headline and `--json` carries `scope.members`, so a coverage number read over several repositories' aggregated scope is never mistaken for one repository's. See [[change-control-gate]] and ADR-016 for the aggregation model. *(test: `workspace-refusals.test.ts` "doctor names the workspace and exposes members in --json")*
- **A directory any walk could not read is disclosed, never absorbed.** All three trees codument walks — source discovery, the docs knowledge base, and workspace member discovery — return what they could not look inside alongside what they found, merged into one list because the user's question is "what could codument not read?", not which internal walk tripped. `doctor` prints it beside the headline with `--json` carrying it additively. Absent is not unreadable: a directory that does not exist (a project with no `docs/` tree, a path that vanished mid-walk) contributes nothing and is not disclosed, because conflating the two would fire on the common case and drown the signal. Silently skipping such a directory shrinks the denominator, and a smaller denominator makes the percentage read *higher* than the truth — the same most-confident-where-most-wrong inversion an undeterminable ignore set produced, arriving by a different route. It rides the return value rather than a callback so a caller can drop a field it can see in the type but cannot forget to pass one. *(tests: `analyze.test.ts` "an unreadable directory is reported, never silently skipped" — the readable half still returned and the unreadable half named, the shrunken denominator surfaced, the docs tree covered because a doc hidden there would silently suppress a link-rot `warn`, the two walks merged, absent distinguished from unreadable, and the walk root named as `.`; `doctor.test.ts` and `scan.test.ts` for the command wiring; `git.test.ts` for the member walk)*
- **A score never appears without the scope that shaped it.** When a project has narrowed the denominator, `doctor` names the declared dirs and globs beside the coverage headline and `--json` carries them additively as `scope.configuredExclusions`; `scan`'s summary names them too. Two repositories' percentages look comparable, and are not, unless what each one counted is on screen next to the number — a denominator narrowed by a project decision is a different denominator, and the score is only publishable because the decision is visible. A project that declared nothing prints nothing, so the common case stays quiet. *(tests: `doctor.test.ts` "names the declared exclusions beside the score, in both surfaces" / "says nothing about a scope nobody narrowed"; `scan.test.ts` "names the declared exclusions in its summary")*
- **A declaration that cannot be understood stops the run; a declaration that cannot be read degrades and says so.** These are different failures and get different answers. Metadata that parses but declares something invalid means the user said a wrong thing: it refuses by name rather than scoring against the defaults, because silently ignoring it would score over a scope they explicitly narrowed — the same silent no-op this configuration exists to end. Metadata that does not parse at all says nothing about whether a declaration exists, so the resolution falls back to the defaults and reports that it could not tell, which keeps an advisory surface (the editor nudge, the version-skew notice) from erroring on a file it only needed to peek at. That report is not optional: it rides the same scope verdict the git half uses, so `doctor` prints it beside the coverage headline and `--json` carries it additively — a widened scope inflates numerator and denominator together, so the figure reads better than the truth exactly when it is least earned. Unknown is never consumed as empty, and never quietly consumed at all. *(tests: `analyze.test.ts` "degrades and reports when the metadata cannot be read at all" / "refuses rather than degrades when a declaration itself is invalid"; `doctor.test.ts` "fails loud through the CLI rather than scoring on an invalid declaration"; `hooks.test.ts` "degrades to the built-in spec rather than crashing on a broken config"; `doctor.test.ts` "discloses that the declaration could not be read, in both surfaces")*
- **A score whose scope could not be verified is published WITH that fact, never as a bare number.** The denominator normally subtracts git's real ignore set; when those rules cannot be determined (no repository at the root, or git itself failing) the scope silently widened to the static exclusion spec alone, admitting build output as first-party source. That failure is not neutral — mapped build output lifts numerator and denominator together, so the percentage reads *better* than the truth, which is how a monorepo whose root was not a repository reported full coverage over a tree that was 37% compiled output: most confident exactly where most wrong. The analysis therefore carries a scope verdict out with the score, `doctor` prints the caveat beside the coverage headline, and `--json` carries it additively (no version bump — a consumer that ignores the field reads exactly what it read before). It is disclosure, not a finding: it never becomes a warning and never moves the exit code, because the repository is not misconfigured — codument simply could not see it. *(tests: `doctor.test.ts` "doctor discloses an unverified scope" — applied inside a repo with no extra output, unavailable-with-reason outside one, the caveat printed beside the number, the additive `--json` field, determinism)*
- **`generated-leakage` judges a registered source against git's real ignore set as well as the static spec, and its evidence names which rule fired.** A repository ignoring a file is a stronger claim than a glob heuristic matching it — the project itself declared that file not worth tracking — so it is checked first and reported in its own words. The lint previously saw only the static spec: `analyze` computed the ignore predicate for the coverage denominator and never passed it down, so a registry holding hundreds of git-ignored build artifacts reported no findings at all. The one check that could have caught the leak had the answer in scope and did not look. A project's own declaration is named as such rather than reported as a built-in heuristic, because the two call for different responses: "you declared this, un-map it or narrow the declaration" is not "codument's guess may be wrong about your file". This is also what keeps a configured exclusion honest — declaring a path the registry still owns silences the gate visibly, never silently. The same attribution answers the authoring path: the refusal a routed file gets cites the rule from this one definition, so the surface that *reports* a leaked source and the surface that *refuses* one cannot name the same rule differently — the drift a second copy of this judgement would eventually produce. **Honest limit:** when the ignore rules cannot be determined this rule cannot fire, so a clean lint never by itself implies a clean scope — which is why the unverified-scope disclosure above exists alongside it. *(tests: `analyze.test.ts` "generated-leakage consults git's ignore set, not only the static spec" — a git-ignored source flagged and attributed to git, a tracked source not flagged, a statically-excluded source still flagged in the spec's own wording, and no git-ignored claim when the rules are undeterminable; "names the project's own rule when a declared path is registered")*
- Coverage and lint are never blended into one number; bloat and other mess stay lint findings and never move the coverage score. *(tests: `analyze.test.ts` lint and bloat suites; `doctor.test.ts` two-axis report)*
- The headline is the equal-weight average of ratios with a non-empty denominator; a zero-denominator ratio is excluded, never scored 0% or 100%, and an all-N/A repo yields a null score, not zero. *(test: `analyze.test.ts` rollup invariance and null-score cases)*
- No wall-clock value enters the score; any freshness window is commit-count based. *(honest boundary — the freshness/drift ratio is re-sourced from the change-control gate and reads N/A here until it lands; the no-`now()` rule is structural in `analyze.ts`)*
- **`--strict` gates on what this change produced, never on what the repo arrived with.** It exits nonzero iff at least one actionable (warn) finding is attributed to the working tree's change set; informational notes never affect the exit code, and bare `doctor`'s output and exit code are unchanged. The rule is the one [[change-control-gate]] settled for inherited registry rot — a gate that fails on inherited state is a gate people learn to bypass — and this surface was the half that never got it: the attribution split shipped as a rendering change while the exit code went on failing over the total, so a field repo read "nothing here gates anything" directly above a red gate on 105 findings, and this repository's own release guide recorded the resulting failure as an accepted baseline for six releases rather than a bar to clear. Reporting is unchanged and deliberately wider than gating: every inherited finding is still named, because the readable half of the split was never the problem. Where attribution cannot be determined at all — no repository to ask — the gate falls back to every finding rather than to none, since "cannot tell" resolving to a green nobody earned is the one outcome worse than a red nobody can clear. The opt-in `--verify-invariants` mode is the stated exception and stays whole-repo: a broken invariant is a cited test that is red *now* rather than debt, and a mode someone invoked to audit the doc estate is asking a whole-repo question by construction — narrowing it to the change set would answer a question nobody asked. *(tests: `doctor.test.ts` "--strict passes on a repo carrying only inherited findings", "--strict fails as soon as this change produces one", "no repository to ask fails closed", and the `--strict` CLI gating suite)*
- **`--verify-invariants` RUNS each cited invariant test; it is opt-in and never changes bare `doctor`.** For every registered doc's `## Invariants & boundaries` marker it runs the cited test through the project's own hardened runner — deduping a test shared by several invariants to one run — and classifies the invariant green / broken (a cited test went red) / unpinned (a cited test is missing or the marker names no test file) / unrunnable (toolchain) / untested / honest. Broken and unpinned are warn results that `--strict` fails on; the honesty ratio scores the enforced (green) share and excludes unrunnable results and deliberate non-testable boundaries. Because it executes tests it is slower and toolchain-dependent, so it is off by default: bare `doctor` and its `--json` stay byte-identical and deterministic, the invariants block appearing only when the mode is on. A marker pins a test when any of its parenthetical spans names a test file — through a `test:`/`tests:` prefix or any prose that names one (codument's own docs write forms like "pinned by the assertions in the named suite") — and a real citation is never shadowed by a trailing aside; the whole file runs (no per-subtest selection). **Honest limit:** like the confirm gate it shares a runner with, the blocking half assumes a TAP-emitting runner — a genuinely red test under a non-TAP reporter (vitest/jest default) exits nonzero with no TAP evidence and reads `unrunnable` (info, fail-open) rather than `broken`, so a non-`node:test` project must point its runner at a TAP reporter to get the blocking behavior — declared once as `testCommand` in `.codument-meta.json` (resolved inside the shared runner, so this mode picks it up without the caller passing anything) or overridden per run with `--test-command`. That limit is now SAID rather than implied: an unrunnable invariant is excluded from the honesty ratio, so without a named line a project whose runner emits no test evidence reads as "nothing to see" when nothing was checked — this mode prints the same condition the adversarial-review gate does — a refused `testCommand` declaration AND the count of invariants nothing could decide, worded by the one shared builder rather than rebuilt here, and carried additively on `--json` so a CI consumer cannot read an all-unrunnable run as a clean one. Reading only the resolved command and discarding the refusal reason is exactly how these two surfaces once disagreed about a single toolchain gap. *(test: `adversarial-review-testcommand-parity.test.ts`)* *(tests: `invariant-check.test.ts` parse/classify/dedup, non-`test:` prose recognition and aside non-shadowing, + the real-runner e2e over a fixture repo; `doctor.test.ts` "bare doctor --json carries NO invariants block"; `review-confirm.test.ts` the runner reports a spawned test's true exit)*
- `doctor` refuses to score a subdirectory of a git repository, for the same reason the change-control gate refuses to gate one: the toolchain treats that root as wrong (git speaks toplevel-relative paths; the registry is keyed below them), and a health score published for a root the gate refuses would let the two surfaces disagree. It exits nonzero naming both paths — under `--json` as a discriminated JSON shape, never human text a machine consumer would crash on — while a standalone non-git directory still scores normally. *(tests: `doctor.test.ts` "errors loudly from a subdirectory of a git repo" and "scores normally at a genuine git toplevel")*
- The badge renders an N/A pill when no ratio applies — never a misleading 0%. *(test: `badge.test.ts` "renders N/A (not 0%)")*
- After a package upgrade the surfaces say so instead of silently lagging: when the project was scaffolded by an older codument than the one running, `doctor` (and `review`) print one dim advisory line naming both versions and the `codument update` fix — human output only (the `--json` contract stays byte-identical), never a finding, never an exit-code input; a corrupt meta file downgrades the nudge to a repair pointer rather than crashing an advisory surface. *(test: `doctor.test.ts` "nudges once, dim and human-only" + the in-sync/corrupt cases)*
- Coverage is registry membership plus dependencies, not doc quality; the command states this in its own output so the number is never mistaken for a quality score. *(enforced by the human-output disclaimer; no semantic test)*
- **`doctor` names the gate's languages from the same manifest the README is parity-tested against** — one truth for the support claim, so the health surface and the docs cannot disagree about what the gate judges. *(test: `language-matrix.test.ts` — README byte-parity, manifest ≡ registered adapters, seeded mismatch goes red)*
- **`path-enumeration` counts distinct non-test paths, so complying with the standard cannot raise it.** The doc standard REQUIRES each invariant to link the test that enforces it, and the smell is "prose restates the file list" — so two calibrations keep the metric pointing the right way. Citations are deduped: three invariants pinned by one spec file are one file cited three times, not a three-file enumeration. And a path following a test convention is exempt from the count everywhere in prose, not only inside the invariants section — a test citation is legitimate wherever it appears, and a section-scoped exemption would only invite heading games. Without these, the finding count rose as a project's docs improved, which trains agents and humans alike to strip test links to quiet `doctor`: a metric that climbs on compliance is not a weak heuristic but a backwards one. A test path stays fully visible to `line-anchor`, because the standard says cite the test, not the line. **Honest bounds:** "a test file" means the built-in conventions, so a project whose own test convention lives only in its `exclude` config is still counted; and the JVM source-set glob is not language-scoped, so any project's literal `src/test/` tree is treated as tests. Both only ever widen an info-only exemption, and both are pinned by test rather than left to be discovered. *(tests: `prose-altitude.test.ts` "path-enumeration counts distinct non-test paths" — the field shape cleared by dedup alone, a five-distinct-test doc cleared by the exemption and firing without it, a source file and its own spec no longer colliding, genuine enumeration still firing; the doctor e2e pair)*
- **The prose-altitude lint reads every registered doc for three named smells, info-only.** `doctor` scores each registered feature/concept doc against the doc standard with three deterministic, lexical heuristics — `symbol-mirror` (a prose line opening with an exported identifier and a verb), `line-anchor` (a `path.ext` reference carrying a `:` line number, which rots on every edit), and `path-enumeration` (a prose section that restates the file list, or a canonical `path — role` Key files entry missing its role). No NLP and no model call, so the reading is reproducible; each is a separate id so soak data judges them independently. They render in doctor's **Notes channel** as info, are excluded from the actionable count, and never fail `--strict` — bare `doctor` exit codes are untouched. Promotion of any id to a warning is deferred to its own false-fire soak (see [[doc-audience-layers]] for the initial baseline and the promotion criterion). The symbol names the heuristics compare against are extracted through the SAME language adapters as the gate, so `doctor` warms WASM-grammar adapters up front and a cold adapter is a loud wiring error — a whole language's symbol-mirror reading can degrade to "no names" only for a genuinely malformed file, never silently for a wiring gap. *(tests: `prose-altitude.test.ts` — each smell fires on a true case and stays silent on its near-misses [code fence, table, copula-not-verb, non-exported opener, a prose Key files sentence vs a bare `path` entry]; the doctor-wiring case that a smell rides Notes as info while `--strict` still exits 0; `doctor.test.ts` "runs green over a Python repo")*
- **A fence reproducing a declaration the entry owns is judged; prose-only reading could not see it.** The three prose smells skip fenced content by construction, which is right for the illustrative examples docs are full of and leaves the purest mirror there is unjudged — a doc carrying a declaration verbatim owes a hand edit every time that declaration moves, and the change-control gate will demand one, which is how this tool came to compel in one surface exactly the rot it forbids in another. `fenced-mirror` closes that: it names a fence in a registered doc that DECLARES a symbol that entry owns, read against the same exported-symbol list `symbol-mirror` uses so "a symbol this entry owns" keeps one definition. A declaration site is required and a mention is not one — a fence that merely calls the symbol is usage, which is what an example is made of. A named shape fires on its own; a value declaration needs an explicit export marker, because a bare one is how every usage example opens, and only the shapes carry the asymmetry because the languages that mark visibility by convention rather than by keyword have no marker to find. One finding per fence, anchored on its first declaration: the reader's fix is to delete the block, not to edit it line by line. Info-only in the Notes channel like its three siblings, so `--strict` exit codes are untouched and its false-fire rate can be soaked before anyone argues for promotion. *(tests: `prose-altitude.test.ts` "prose-altitude: fenced-mirror" — the field's verbatim-union shape; shape-vs-value declarations; usage, CLI-output and config fences silent; a name the entry does not own silent; one finding per fence anchored on the first declaration; a fence left unclosed at end of file; plus the doctor-wiring case that it rides Notes as info while `--strict` still exits 0)*
- **What this change produced is not what the repo arrived with, and the health surface says which is which.** Seventy findings on a maintained repo reads as a surface that cries wolf, and the diagnosis matters: the cause is upgrade debt, not calibration. Every lint added since a project adopted retroactively finds old violations, so the count climbs on upgrade even when the repo has not moved. The consequence is the defect — sixty-nine inherited findings and the one just introduced rendered identically, so the loop's only whole-repo health surface was unreadable at exactly the moment it had something new to say. The split is **derived, never a baseline file**: a finding is this change's when its own subject file is in the working tree's change set, which is the same scope rule `review` uses and leaves no second source of truth to rot. Attribution is deliberately the tightest reading — by FILE, never by feature, because marking every pre-existing finding on a feature as new the moment someone edits one of its files rebuilds the same unreadable pile from the other side, and the entire value of the split is that the short list can be trusted. A finding with no subject file has nothing to match and stays inherited, for the same reason. Outside a repository the split is **absent, not empty**: the change listers answer "nothing changed" there rather than refusing, and reporting every finding as inherited on that basis would be the unknown-is-not-empty conflation this codebase refuses everywhere else. Nothing about gating moved — `doctor`'s findings were always warnings. *(tests: `doctor.test.ts` "doctor separates what this change produced from what the repo arrived with" — a finding attributed only when its own file was touched, the human surface leading with it, and a non-repo carrying no split at all)*
- **The mechanical half of the pile clears in one command, and the command says what it refused to touch.** Separating inherited debt from new findings makes the surface readable; it does not make the debt smaller, and an adopting repo's inherited count is real work nobody schedules. `doctor --fix` clears the subset that needs no judgment by dropping the false claim, and the qualifying test is whose word contradicts the registry line: a claim the **project itself** has already refuted is transcription to remove, not a decision. That covers a path that is not on disk, its pattern twin (a declared tree matching nothing), a path the repository's own ignore rules exclude, and a path the project's own `exclude` block covers. Every edit is reversible by construction: it only ever REMOVES a path from an entry's source list, never adds one, re-points one, or touches a doc, so a wrong guess cannot put corruption *into* the control plane, which is the state this surface exists to detect. The line it will not cross is judgment: where a manifest belongs is what wakes, an unmapped file needs an owner, and a doc-level finding invites the compaction theater that an agent pointed at seventy findings reliably writes. **A codument heuristic is not the project's word, so it is on the far side of that line** — the built-in out-of-scope rules read names, and the same rule that catches build output calls a hand-authored data file generated; clearing a registration on the strength of the tool's own guess is the tool overruling a human claim with a heuristic, which is a worse failure than leaving the line for a reader. Because one lint can land on either side depending on which rule fired, the analyzer marks each finding rather than the command matching on lint ids, so every surface asking "may this be cleared?" gets one answer. Whatever is left is counted by kind and named as left alone, always — a command that clears part of a pile and says nothing about the rest reads as having cleared the pile. The report it prints afterwards is the state the fix left, not the one it found. *(tests: `doctor.test.ts` "doctor --fix clears what needs no judgment, and says what it left" — the false pointer dropped while every real claim survives, the judgment call named and untouched, no doc modified, idempotent with a plain word when there is nothing mechanical left, and the report below reflecting the post-fix state; "doctor --fix clears the out-of-scope claims an upgrade leaves behind" — the gitignored and declared-exclusion claims dropped together, the heuristic-only claim kept and named as needing a decision; `analyze.test.ts` "a finding says whether clearing it is transcription or a judgment" — the three-way split at the source, with the previously-clearable pair still marked)*
- **A dependency manifest is something a doc is affected by, never something it owns.** Ownership means a wake: every edit asks the owning doc whether its documented contract moved. A lockfile is a machine-written resolution artifact with no contract for any doc to carry, and a manifest moves on every version bump and script tweak — so in the field a `bun.lock` line woke an ADR about deferring native voice modules and a `package.json` line woke a getting-started page, on changes neither document could possibly be wrong about. Six of that session's eight acknowledgments were spent on files with no symbols in them. The concept that fits already exists and is one field over: `related_sources` claims impact and never wakes. So an owned manifest is **named, and never rewritten** — moving a source between the two changes what wakes, which is the user's call, and a project that genuinely documents its packaging keeps the claim and this line with it. The set is a fixed list of names across the ecosystems the adapters already cover rather than a heuristic, because a lint that guesses at what a manifest is would fire on real source called `package.ts`. *(tests: `analyze.test.ts` "a manifest claimed as an owned source" — the field replay naming both files with the fix, the same file as an impact claim staying silent, real source never mistaken for packaging, and the name list across ecosystems)*
- **A declared tree is a registration, so every question the analyzer asks of a source is asked correctly of a pattern.** A tree source owns the in-scope files it matches — the same ownership N literal lines would have produced, which is what keeps the health surface from punishing the cheaper registration: a correctly-registered tree used to score zero and produce a finding per file, because a glob is not a path on disk and every source question was a path question. Two findings replace what a path question cannot ask. `unmatched-pattern` is the tree form of a vanished source: a declared tree that names nothing governs nothing, so every file someone believed was covered is ungoverned — asked by walking the pattern's own literal prefix, because the trees most worth registering (a locale pack, a content tree) sit outside the source scope entirely and both the coverage denominator and git's tracked set would answer "nothing" for a tree doing its job. `shadowed-source` names a path an entry's OWN tree already covers: the line only restates the pattern, or — in `related_sources` — claims impact-only for a file the same entry owns outright. It is deliberately scoped to the entry, because the same path under ANOTHER entry is the sanctioned refinement that promotes one file out of a tree without dismantling it. Ownership resolves against the discovered source set, which is also what keeps a locale tree out of the score while it governs the gate: it was never in the denominator to begin with. *(tests: `analyze.test.ts` "a declared tree is a registration, not a missing path" — a tree owning its files at full ownership with neither `unmapped-source` nor `missing-source`, a tree matching nothing named, a path shadowed by its own entry's tree in both source fields, and the cross-entry refinement staying silent)*
- **The compaction the standard mandates is checked, not merely written down.** A doc whose delivery checklist is fully checked is named: the standard requires a shipped doc to carry only its durable layers — the checklist, acceptance criteria and verification strategy compact out when the last step lands, and whatever outlived the work moves to Decisions or an ADR. Every other doc question was already asked (bloat, thinness, link rot, altitude) and this one, the most explicit rule the standard has, was asked by nobody, so it held only where somebody remembered. That is the enforcement gap the tool exists to close, and this repository was inside it: the finding fired on two of its own docs the moment it existed. It waits for *every* step to be checked, because an in-flight checklist is doing exactly its job and a doc that shipped one effort while starting another is still working. And it names the doc without touching it — what survives compaction is a judgment about which decisions outlived their plan, which is the whole point of the exercise and stays the author's. *(test: `analyze.test.ts` "a shipped doc that still carries its checklist is named" — a fully-checked plan fires with its step count, an in-flight one stays silent, and a properly compacted doc stays silent)*
- **Section awareness works on every checkout, and a Decisions layer that points at nothing is named.** The heading match had never succeeded on a CRLF checkout — a carriage return is a line terminator in JavaScript, so `.` does not match one and every heading in the file read as not-a-heading. Section scoping was therefore silently dead on Windows: every doc reported against the whole document at line 0, which also defeated the Key files exemption and produced `path-enumeration` findings the calibration explicitly says must not fire. That is the worst shape a heuristic can take — firing *because* a doc complies — and it was invisible because the finding still looked plausible. One split fixes all four smells at once. **The same split was owed everywhere a doc is read, and scoping it to the surface that reported it left the defect shipping under every other caller** — the bloat lint, the invariants parser, the review bundle's section extraction and plan scope each kept their own line split, so on Windows the bloat lint attributed whole documents to one untitled section and named two of this repository's own docs for six releases, recorded in the release guide as an accepted baseline rather than read as the bug it was. A platform-conditional parse is invisible to a suite that runs on one platform, so the guarantee is asserted as parity between the two encodings across every doc parser at once, rather than per smell as each is noticed. On top of it sits `unsourced-decision`: the standard says the Decisions layer is pointers, "the durable why; reference, never restate", and a layer that cites nothing records a conclusion nobody can re-derive or contest — which is how a wrong recorded decision survives the attempts to fix what it was wrong about. It is judged per SECTION, not per bullet: an individual small decision legitimately has no ADR, and a per-bullet rule would only pressure authors to decorate every line. A link, a wiki-link, an ADR by number or a test citation anywhere in the layer satisfies it. Info-only in the Notes channel with its siblings, so `--strict` exit codes do not move. *(tests: `prose-altitude.test.ts` "section awareness survives CRLF" — the same reading on both line endings, the enumerating section named with the Key files entries still exempt, and a section-scoped smell firing at all where none could before; "a decisions layer that points at nothing" — a layer of bare conclusions fires once, each evidence form silences it, an empty layer and another section's uncited prose stay silent)* *(test: `crlf-parity.test.ts` — every doc parser reads CRLF as LF, the bloat lint naming its real section rather than a synthetic preamble, proven to bite against the seeded split)*
- **`empty-depends-on` answers its own question: it names the edges codument can derive from the imports, and names them as a floor.** The finding used to send the user off to hand-assemble a graph codument could already read, and every hand-maintained derivative drifts. The edges ride the existing finding — same id, same severity, same firing conditions — so soak data stays comparable and nothing about the exit code moves; an entry with nothing derivable keeps its original wording and gains no `--json` key at all. They are worded as what codument *could derive*, never as the entry's dependencies: import resolution sees only the coupling expressible as an import, so runtime wiring or a shared data shape yields a real edge with no import to read, and a user who reads a partial set as complete stops looking exactly where these edges are load-bearing. An edge is dropped rather than guessed — one landing on a file no entry owns, one pointing back at its own feature, and one whose resolved target does not exist, because the resolver is best-effort and a guess that missed must not return a confident edge to a file nobody imports. Nothing is written to the registry; the user still decides. *(tests: `analyze.test.ts` "empty-depends-on carries the derived edges as evidence" — the floor wording and evidence when edges exist, byte-identical output when none do; "deriveDependencyEdges" and "deriveDependencyEdges never invents an edge from a resolution guess" for the derivation)*
- A foundation entry (other entries depend on it; it declares no dependencies) is excluded from the dependency-coverage denominator and never raises an empty-depends-on finding — empty `depends_on` is flagged only on an isolated entry that nothing depends on. *(test: `analyze.test.ts` empty-depends-on foundation-exemption — flags an island, never a depended-upon foundation; the change-control fixture exercises both, `db` exempt + `notifications` flagged)*
- The tool never warns about its own seconds-old scaffolds, and a true leaf has an honest way out: a `needs-review` entry (the state a fresh `scan` writes) is in-flight — exempt from empty-depends-on and outside the dependency ratio, same rationale as the thin-doc exemption — so the recommended first run (`init → scan → doctor --strict`) ends green with a sane headline; and a reviewed leaf that genuinely depends on nothing clears the finding explicitly with `depends_on_confirmed: true` (the foundation exemption needs inward edges a leaf cannot have). A mature, isolated, unconfirmed entry still fires. **The exemption reasons about seconds and is implemented as forever, so the count is disclosed rather than left silent**: `doctor` names how many entries are still scaffolds, but only once the tree has moved past the scan that wrote them — measured against that scan's own recorded file count, never a clock, because no wall-clock value may enter this report and a fresh scan must stay byte-identical. It sits beside the score with the same standing as a declared exclusion, since it shaped the score; it is never a finding and never an exit-code input, and a meta file that will not parse degrades it to "cannot tell" rather than taking an advisory surface down. A field registry sat at `needs-review` for four months, outside every ratio, reading as in-flight, while `lastScan` still recorded 292 source files against 404 on disk. *(tests: `analyze.test.ts` "scaffold exemption + confirmed leaf"; `scan.test.ts` "fresh scan → doctor: the first run ends green"; `doctor.test.ts` "a scaffold the tree has moved past is disclosed, never scored" — silent at parity, disclosed once the tree moves, zero once reviewed, null with no recorded scan, and the strict exit unmoved)*
- A doc claimed done (status `current`) but with no narrated orientation layer is flagged as a thin-doc (info) — the "half-documented reads green" gap the freshness gate cannot see, since a fresh-but-unmoved doc passes freshness. A scaffold or in-flight doc (needs-review / draft) is exempt. *(test: `analyze.test.ts` doc-integrity — thin-doc fires on a current stub, not on a Summary/In-plain-terms/needs-review doc)*
- A dangling intra-repo link or `[[wikilink]]` in any `docs/` file is flagged as link-rot (warn); external URLs and fenced code examples are ignored, and anchors are not resolved (file-existence only). *(test: `analyze.test.ts` doc-integrity — flags dead links and wikilinks, ignores valid/external/fenced)*
- A `depends_on` edge naming no registry entry is flagged as dangling (warn). The graph is load-bearing — change review fans impact out along it and the dependency ratio reads it — and its consumers drop an unresolvable edge without a trace, so a dangling edge silently weakens both; the target is either an unregistered entry (register it) or a typo (fix the slug). *(test: `analyze.test.ts` graph-integrity — fires per unresolvable edge, never on one that resolves)*
- **Every owned file whose gate the risk rule takes away is named here, with the line that gives it back.** A file a feature claims as primary that no adapter can read is gated only where an owner declares a `risk` ([[change-control-gate]]); without one its content changes are reported and never blocked. The change surface says so for the files you touch, which leaves the ones you do not touch — on a project upgrading from a release where all of them gated, that is most of them, and a downgrade someone has to discover by not being stopped is the quiet green this whole surface exists to prevent. So the whole-registry view names each one, its owner, and the declaration that restores the block. Info, never warn, and never an exit-code input: the state is a consequence of a decision the tool made, not a defect the project left behind, and a reader who sees the list and shrugs has answered correctly. An excluded file and an impact-only claim are both absent — neither lost anything, and each has its own finding for its own reason. *(test: `analyze.test.ts` "unread-owned" — the blind owned files are named with their remedy, a readable source is not, a declared risk silences it, and neither an excluded nor a related-only claim appears)*
- A feature or concept page no registry entry points at (neither as its `doc` nor in any `docs` list) is noted as an orphan (info). Staleness is keyed on the registry, so the gate structurally cannot cover an unowned page — it rots silently no matter how load-bearing it reads. Info, never warn: a deliberately registry-free page is legitimate, so the note asks "own it or know why not" rather than failing CI; pages outside `docs/features|concepts` are never flagged. *(test: `analyze.test.ts` graph-integrity — notes the unowned page only; owned and out-of-tree pages stay silent)*

- The registry v2 model that coverage and lint read directly, with no migration path: [001-registry-v2-model-no-migration](../architecture/decisions/001-registry-v2-model-no-migration.md).
- `doctor` is documentation coverage — the two-axis split and the opt-in `--strict` gate: [002-doctor-is-documentation-coverage](../architecture/decisions/002-doctor-is-documentation-coverage.md).
- A registry entry can govern a tree, so a source is a path or a pattern: [018-a-registry-entry-can-govern-a-tree](../architecture/decisions/018-a-registry-entry-can-govern-a-tree.md).

## Key files

- `src/commands/doctor.ts` — the command orchestrator: assembles the two-axis report, applies the opt-in `--strict` exit policy, renders human and `--json` output plus the on-disk coverage artifact, and — under the opt-in, environment-touching `--verify-invariants` — runs the invariant check and folds its broken/unpinned warnings into the strict exit (bare doctor stays byte-identical, so its `--json` gains the invariants block only when the mode is on).
- `src/lib/analyze.ts` — the deterministic analyzer: computes the coverage ratios and their rollup, emits the lint findings, and resolves the project's declared scope over the canonical exclusion spec. This is the shared engine the rest of the health surface reads. The spec's own definition lives beside it in [[lib]] (`exclusion-spec.ts`), a leaf module so the git seam can reuse the same directory list without importing the analyzer.
- `src/lib/badge.ts` — the rendering seam: turns a coverage percent (or N/A) into a static, network-free SVG badge.
- `src/lib/prose-altitude.ts` — the deterministic altitude heuristics: a pure, lexical reading of a registered doc for the "mechanism in the doc" smells the standard forbids — a symbol mirror (prose restating an exported identifier and verb), a file-line anchor (`path.ext:NNN`, which rots on every edit), path enumeration (a prose section restating the file list), and a fenced mirror (a code block reproducing a declaration the entry owns — the one that reads inside fences rather than skipping them). No NLP and no model calls; info-only by contract, so it never fails the gate.
- `src/lib/invariant-check.ts` — the engine behind the opt-in `--verify-invariants` mode: it parses a doc's `## Invariants & boundaries` markers into machine-checkable test pointers, then runs each cited test through the project's own hardened runner (deduping a shared test to one run) and classifies the invariant — green, broken (a cited test went red), unpinned (a cited test is missing or the marker is unparseable), unrunnable (toolchain), untested, or an honest non-testable boundary — with an honesty ratio over the enforced share. This is what turns "this doc's invariants are enforced" from decoration into a checkable claim.
